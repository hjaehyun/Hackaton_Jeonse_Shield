# 전세방패 — 실거래가 연동 설계서

작성일: 2026-09-21
대상 범위: 목업 데이터를 국토교통부 실거래가 API 실데이터로 교체하는 작업
현재 상태: 화면 3개와 계산 로직은 완성, 데이터만 고정 목업

---

## 1. 무엇을 만드는가

이용자가 **지역 · 단지 · 전용면적 · 보증금**을 입력하면,
같은 단지의 **실제 매매 거래**를 조회해 전세가율을 계산하고 위험 구간을 판정한다.

이 절은 실거래가 연동을 시작할 때 쓴 범위 정의다. 그 뒤 실제로 무엇이 들어왔는지
현재 상태를 함께 적는다.

### 범위에 들어가는 것 — 전부 완료

- 실거래가 API를 호출하는 Worker 프록시 라우트
- XML → JSON 변환과 정규화 (`src/lib/rtms.js`)
- D1 기반 응답 캐시
- 단지명 후보 선택 UI (자동 매칭 대신 이용자가 고른다)
- 표본이 없을 때의 정직한 실패 화면

`mockTrades` 배열은 제거됐다. 브라우저 검사가 번들에 다시 들어오면 실패시킨다.

### 이 문서를 쓸 때는 범위 밖이었으나 그 뒤 구현된 것

- 법령·판례 API 연동 (`/api/law`, D1 캐시 7일) — 실데이터로 동작 중
- LLM 요약 (Upstage Solar, 판시사항 원문 병기 + 폴백)
- 전세 시세 대비 메인 지표 (2026-09-22, 11-c절)

### 여전히 범위 밖

- 연립다세대·단독다가구
- 로그인, 결과 저장, 지도

## 2. 제약

설계를 지배하는 것은 런타임 제약이다.

| 제약 | 값 | 출처 |
|---|---|---|
| CPU | 요청당 10ms (무료 플랜) | Cloudflare Workers |
| 서브리퀘스트 | 요청당 50개 | Cloudflare Workers |
| 바인딩 | **D1, R2만.** KV 금지 | Genspark 호스팅 배포 검증 |
| API 쿼터 | 일 10,000건 (개발계정) | 공공데이터포털 |
| API 응답 | XML 전용 | 국토교통부 |
| 마감 | 2026-09-27 22:00 | 해커톤 |

**CPU 10ms가 실질적 설계 제약이다.** 네트워크 대기는 계산에 들어가지 않지만 파싱은 들어간다.
그래서 범용 XML 파서를 쓰지 않고, `numOfRows`를 낮추고, 캐시로 파싱 자체를 건너뛴다.

## 3. 아키텍처

```
[브라우저]
   │  지역·월 조합마다 한 번씩, 병렬. 같은 오리진이라 CORS 없음
   │  집계(단지 묶기·해제 거래 제거)는 여기서 한다
   ▼
[Cloudflare Workers · Hono]      invocation 1회 = 1개월치 = 파싱 1건
   │
   ├─▶ D1 (binding: DB)          cache 테이블, kind+lawdCd+ym 단위
   │
   └─▶ apis.data.go.kr            serviceKey 는 서버에만 존재
         ├─ RTMSDataSvcAptRent    전월세
         └─ RTMSDataSvcAptTrade   매매
```

### 왜 브라우저가 월별로 나눠 호출하는가

CPU 10ms는 **Worker 호출 1회당** 예산이다. 한 요청이 12개월치를 처리하면
한 invocation 안에서 최대 1.2MB의 XML을 훑게 되고, 캐시가 있어도 첫 요청은
반드시 그 비용을 전부 치른다. 캐시 히트여도 12개 블롭을 `JSON.parse` 해야 한다.

실측(2026-09-21, 서울 종로구): 호출당 185~246ms, 응답 29KB~134KB.

그래서 **부채질(fan-out)을 브라우저로 옮긴다.** Worker 호출 하나는 한 지역·한 달만
처리하므로 파싱이 1건으로 고정된다. 브라우저는 같은 오리진으로 병렬 요청하고
(HTTP/2 멀티플렉싱), 집계는 순수 함수로 클라이언트에서 수행한다.

`src/lib/rtms.js`는 빌드 시 `public/lib/`로 복사되므로 서버와 브라우저가 같은
정규화·키 생성 코드를 공유한다.

### 서버 프록시를 쓰는 이유

실측 결과 `apis.data.go.kr`는 200 응답에도 `Access-Control-Allow-Origin`에
요청 Origin을 에코한다. **CORS 때문이 아니다.**

브라우저에서 직접 호출하면 `serviceKey`가 개발자도구 네트워크 탭에 노출되고,
프론트엔드 번들에 들어간 값은 공개 GitHub 저장소에 그대로 올라간다.
키를 서버에 가두는 것이 프록시의 유일한 존재 이유다.

## 5. 설계상의 두 가지 어려움

### 5.1 매매 응답에 `aptSeq`가 없다

전월세에는 단지 고유 ID인 `aptSeq`가 있지만 매매에는 없다.
전세가율은 `보증금 ÷ 같은 단지 매매 중위가`이므로 두 데이터를 이어야 하는데,
이을 수 있는 키가 **단지명 문자열뿐**이다.

**대응:** `complexKey()` (구현·테스트 완료)

```
괄호 제거 · 공백 제거 · 소문자화, 숫자는 보존

광화문스페이스본(101동~105동)  →  광화문스페이스본
e편한세상 신촌 / E편한세상신촌   →  같은 키
아남아파트 3차 / 아남아파트 2차  →  다른 키
```

**받아들이는 손실:** 괄호 안 내용만 다른 두 단지는 한 키로 합쳐진다.
`aptSeq`가 없는 이상 "동 범위 표기"와 "진짜 다른 이름"을 구분할 방법이 없다.

**설계 결정 — 자동 매칭을 하지 않는다.**
이용자가 단지명을 자유 입력하면 오타·약칭·표기 차이로 매칭이 실패한다.
실패하면 "표본 부족"이 나오는데, 이용자는 그것이 *데이터가 없어서*인지
*이름을 잘못 써서*인지 알 수 없다.

그래서 **입력 대신 선택**으로 바꾼다. 시군구를 고르면 그 지역에 실제로 거래가 있는
단지 목록을 받아 이용자가 고른다. 고른 단지는 키가 확정되므로 매칭이 실패하지 않는다.

### 5.2 해제된 거래가 섞여 있다

`cdealType`이 비어 있지 않으면 국토교통부가 나중에 취소 처리한 거래다.
중위가는 전세가율의 분모이므로, 취소된 거래가 남아 있으면 판정이 통째로 틀어진다.

**대응:** `activeTrades()` (구현·테스트 완료)로 계산 전에 제거한다.

## 6. API 계약

모든 라우트는 같은 오리진이며 인증이 없다. 실패는 HTTP 상태와 `error` 코드로 표현한다.

라우트는 하나뿐이다. 한 번의 호출이 한 지역의 한 달만 담당한다.

### `GET /api/month`

```
쿼리   kind=rent|trade    (필수)
       lawdCd=11110       (5자리 숫자, 필수)
       ym=202606          (YYYYMM, 필수)

200    {
         "kind": "trade",
         "lawdCd": "11110",
         "ym": "202606",
         "rows": [
           { "name": "명륜동주상복합아남아파트", "key": "명륜동주상복합아남아파트",
             "area": 59.36, "price": 89500, "floor": 3,
             "year": 2026, "month": 6, "day": 17,
             "buildYear": 1999, "dong": "명륜2가", "cancelled": false }
         ]
       }
```

- `rows`는 `normalizeRent` / `normalizeTrade`를 거친 형태 그대로다.
- **해제 거래를 제거하지 않는다.** 몇 건을 걸렀는지 이용자에게 알려야 하므로
  제거는 집계 단계에서 한다.
- 캐시 키는 `kind:lawdCd:ym`이며 TTL 24시간이다.

### 집계는 클라이언트가 한다

`public/lib/aggregate.js`의 순수 함수들이 여러 달의 `rows`를 받아 화면에 필요한
형태로 만든다. 서버 왕복이 없으므로 기간을 다시 넓힐 때 재조회가 필요 없다.

| 함수 | 역할 |
|---|---|
| `listComplexes(tradeRows, rentRows)` | `key`로 묶어 `{ key, name, tradeCount, rentCount }` 목록. 거래 수 내림차순 |
| `complexTransactions(key, tradeRows, rentRows)` | 한 단지의 `{ trades, rents, cancelledCount }`. `trades`는 해제 거래 제거 완료 |

`name`은 표기가 여럿일 때 가장 최근 거래의 것을 쓴다.

### 오류 응답

| 상태 | `error` | 뜻 | 화면 처리 |
|---|---|---|---|
| 400 | `INVALID_PARAMETERS` | 파라미터 형식 오류 | 입력 단계로 되돌림 |
| 502 | `UPSTREAM_UNAVAILABLE` | 공공데이터포털 응답 실패·타임아웃 | "조회 실패, 잠시 후 다시" |
| 503 | `KEY_NOT_CONFIGURED` | 서버에 키가 없음 | 동일 |

**오류 본문에 업스트림 URL이나 예외 메시지를 넣지 않는다.** 둘 다 `serviceKey`를 포함할 수 있다.

## 7. 캐시

### 왜 필요한가

1. CPU 10ms — 캐시 히트면 XML 파싱이 일어나지 않는다
2. 일 10,000건 쿼터 — 같은 지역·월을 반복 조회하지 않는다
3. 응답 속도 — 시연에서 체감 차이가 크다

한 번의 진단은 6개월 기준 **12회 업스트림 호출**(전월세 6 + 매매 6)이 필요하다.
브라우저가 병렬로 보내므로 체감은 1회 왕복에 가깝지만, 캐시가 없으면 같은 지역을
두 번째 조회할 때도 12회를 다시 쓴다.

### 스키마

D1에는 TTL이 없다. 만료를 컬럼으로 직접 관리한다.

```sql
CREATE TABLE IF NOT EXISTS cache (
  k          TEXT PRIMARY KEY,
  v          TEXT NOT NULL,
  expires_at INTEGER NOT NULL
);
```

키는 `rent:<lawdCd>:<ym>` / `trade:<lawdCd>:<ym>` — **업스트림 호출 단위로 캐시한다.**
라우트가 월 단위이므로 캐시 단위와 요청 단위가 1:1로 맞는다.

TTL 24시간. 실거래가는 신고 기준이라 그보다 자주 바뀌지 않는다.

### 동작 규칙

- 테이블은 Worker가 첫 요청에서 `CREATE TABLE IF NOT EXISTS`로 만든다.
  배포 경로에서 마이그레이션을 돌릴 수 없을 수 있기 때문이다.
  모듈 레벨 플래그로 아이솔레이트당 1회만 실행한다.
- 쓰기는 `c.executionCtx.waitUntil()`로 빼서 응답을 지연시키지 않는다.
- **D1 바인딩이 없어도 서비스는 동작해야 한다.** 캐시 계층은 없으면 통과한다.
- 만료된 행은 조회 조건에서 걸러진다. 별도 청소 작업을 두지 않는다.

## 8. 화면 변경

### 위저드 2단계: 자유 입력 → 후보 선택

```
현재   [텍스트 입력]  "예: 전세방패 아파트"
변경   [목록]         종로구에서 최근 6개월 거래가 있는 단지
                     검색어로 좁히기 가능
                     "찾는 단지가 없나요?" → 이유 안내
```

목록이 비면 그 지역·기간에 아파트 거래가 없다는 뜻이다. 그대로 말한다.

### 위저드 3단계: 계약 종류를 묻는다 (2026-09-24)

```
현재   월세 [0]  "전세는 0을 입력하세요"
변경   [전세] [월세]  → 월세 입력칸은 월세를 골랐을 때만 나타난다
```

"월세 0 = 전세"는 **독자가 배워야 하는 규칙**이었다. 처음 계약하는 사람이
대상인데 안내문을 읽어야 올바르게 입력된다. 고르면 끝나는 쪽으로 바꿨다.

검증도 따라 갈린다. 전세면 월세를 묻지도 검사하지도 않고, 월세면 1 이상을
요구한다. 월세 0원짜리 월세 계약은 그냥 전세이므로 모순된 입력이 불가능해진다.

월세 → 전세로 되돌리면 입력값을 지운다. 숨겨진 칸에 값이 남으면 리포트가
전세 계약을 월세로 설명한다.

### 결과 화면

추가로 표시할 것:

- 조회 기간 (`2026.04 ~ 2026.09`)
- 전월세 건수와 매매 건수
- 해제 거래를 걸렀다면 그 건수
- 표본이 3건 미만이면 비율을 내지 않는다 (전세·월세·매매 각각 따로 판단)

카드 구성은 2026-09-22 ~ 24에 두 번 바뀌었다. 11-c·11-d절 참조.

```
① market-card   전세 계약 → 같은 단지 전세 시세와 비교   (메인)
                월세 계약 → 같은 단지 월세 시세와 비교
② ratio-card    보증금 반환 위험 — 전세가율
③ recent-card   이 단지 최근 실거래 (전세·월세·매매 타일 3개 → 팝업)
```

①과 ②는 중위가를 낸 실거래를 표로 함께 싣는다. 중위가는 요약이고, 요약을
못 믿는 독자는 그 근거가 된 행을 읽을 수 있어야 한다. 목록과 중위가는 같은
필터 함수에서 나오므로 구조적으로 어긋날 수 없다.

목록은 **기본으로 펼쳐 둔다.** 처음에 접어 뒀더니 로컬 테스트에서 첫 사용자가
이미 있는 기능을 없다고 보고 다시 요청했다. 위의 차트가 답처럼 보이고 접힌
영역은 각주처럼 보인다. 비교 화면에서 사람이 원하는 것은 금액이므로 금액을
클릭 뒤에 두지 않는다. 차트는 그 행들의 요약이므로 목록 아래로 내렸다.

### 표본이 부족할 때

지금도 `verdict()`가 `표본 부족 — 판정 불가`를 반환한다. 이 동작을 유지하되,
**이유를 구분해서** 알린다.

| 상황 | 문구 |
|---|---|
| 매매 거래가 아예 없음 | "이 단지는 최근 6개월 매매 거래가 없어 전세가율을 계산할 수 없습니다" |
| 유사 면적 매매가 3건 미만 | "전용 84㎡ 부근 매매가 2건뿐이라 중위가를 신뢰할 수 없습니다" |
| 기간을 넓히면 될 수 있음 | "12개월로 넓혀 다시 조회" 버튼 |

**절대 하지 않는 것:** 표본을 늘리려고 면적 허용범위(±10%)를 임의로 넓히거나,
값을 보간하거나, 다른 단지 거래를 섞는 것.

## 10. 정확성 원칙

이 서비스의 가장 큰 결함은 틀린 숫자를 자신 있게 보여주는 것이다.

1. **표본 3건 미만이면 비율을 표시하지 않는다.** 이미 구현되어 있다.
2. **해제 거래를 제외한다.**
3. **화면에 찍히는 모든 숫자는 관측값이다.** 패딩·보간·추정값을 표시하지 않는다.
   (차트 축 레이블이 이 원칙을 어겨 2026-09-21에 수정했고, 회귀 검사로 고정했다.)
4. **실거래가는 신고 기준**이라 최근 1~2개월이 누락될 수 있다. 화면에 명시한다.
5. **월세 계약은 전세가율을 내지 않는다.** 전월세 전환율을 임의로 가정하지 않는다.
6. **이 진단이 확인하지 못하는 것**(권리관계·선순위 근저당·임대인 채무)을 결과 화면에 명시한다.

## 11-b. 알려진 한계 — 한 달에 200건만 받는다

`numOfRows=200`, `pageNo=1`로 **첫 페이지만** 받는다. 페이지네이션이 없다.

| 지역 | 2026-06 전월세 실제 | 받는 건수 | 누락 |
|---|---|---|---|
| 강남구 `11680` | 2,096 | 200 | 1,896 |
| 광주 서구 `12240` | 355 | 200 | 155 |
| 수원 장안구 `41111` | 337 | 200 | 137 |

### 잘리는 형태 (실측, 강남구 `11680` 2026-06 매매)

| 관측 항목 | 값 |
|---|---|
| 받은 행 | 200 |
| 일자 범위 | 1일 ~ 30일 |
| 5일 단위 분포 | 45 / 30 / 30 / 34 / 28 / 33 |
| 포함된 법정동 | 14개 (강남구 전체) |

**월말이 통째로 빠지지 않는다.** 날짜와 법정동이 고르게 섞인 부분표본이다.
이전 판 문서에 있던 "월 내부 순서대로 잘려 월말이 빠진다"는 서술은 관측과
맞지 않아 철회한다.

### 실제 비용 — 단지별 표본 깊이

같은 응답에서 200행은 110개 단지에 흩어졌고, 매매 3건 이상인 단지는 19곳,
1건뿐인 단지가 72곳이었다. 거래가 많은 구일수록 실제 거래량 대비
`thin-sample` 판정이 자주 나온다. 브라우저가 6개월(`MONTHS = 6`)을 조회하므로
단일 월 수치보다는 완화된다.

### 고치지 않기로 한 이유

`totalCount` 페이지네이션은 요청당 CPU 10ms 예산이 이미 제약하는 파싱 비용을
배로 늘린다. `ROWS_PER_MONTH = '200'`은 애초에 그 예산을 지키려고 낮춘 값이다.

표본이 얇으면 비율을 표시하지 않는 것이 11절의 원칙이고 이미 구현돼 있으므로,
이 절단은 **틀린 숫자를 만들지 않고 적용 범위만 줄인다.** 그래서 해커톤 범위에서
제외한다. 같은 내용을 `src/lib/rtms-client.js`의 `ROWS_PER_MONTH` 주석에 남겼다.

나중에 고친다면 `CACHE_VERSION`을 함께 올려야 기존 200행 응답이 하루 동안
계속 나가는 일을 막는다.

## 11-c. 전세 시세 대비 — 메인 지표 (2026-09-22)

### 왜 만들었나

전세가율은 **"경매로 넘어가면 보증금이 돌아오나"** 에 답한다. 그건 매매가의 문제이고,
옆집 전세가 얼마인지는 상관이 없다. 반면 **"내가 바가지를 썼나"** 는 같은 단지 전세
실거래만 답할 수 있다. 랜딩이 묻는 질문은 후자인데 화면에는 전자만 있었다.

답할 데이터는 이미 받아 오고 있었다. 시군구 선택 시 매매 6개월 + 전월세 6개월
= 12개 요청이 나가는데, 전월세는 단지 목록 건수 표시에만 쓰이고 리포트에서
버려졌다. `contract.rents` 가 담기기만 하고 읽히는 코드가 없었다. 추가 호출 0.

### 계산

```
전세 시세 대비 = 보증금 ÷ (같은 단지, 전용 ±10%, 월세 없는 전세 보증금의 중위가) × 100

< 100%     시세보다 낮음
100~110%   시세 수준
110% ~     시세보다 높음

전세 3건 미만 → 비교하지 않음
```

`src/lib/ratio.js`: `similarDeposits` / `marketRatio` / `marketVerdict` / `depositDistribution`.
Q1/Q3은 매매 쪽과 같은 nearest-rank. 보간하지 않는다.

### 규칙

**월세를 전세로 환산하지 않는다.** 보증금 5,000에 월세 70인 계약은 전환율을
가정해야만 전세 보증금과 비교된다. 가정하는 순간 어느 신고에도 없는 숫자가 화면에
찍힌다. 그래서 표본에서 `monthlyRent > 0` 을 빼고, **계약 자체가 월세면 비율을
내지 않고 분포만 보여준다.**

보증금 3,000만원 ÷ 전세 중위가 123,000만원 = 2.4% 에 `시세보다 낮음` 이 붙으면,
종류가 다른 계약에 대해 참이 아닌 문장이 된다.

**위험 등급이 아니다.** 시세보다 비싸게 계약하는 것은 높은 전세가율처럼 위험한
일이 아니므로 밴드 이름은 위치만 말하고 경고색을 쓰지 않는다. 100~110%를
`시세 수준` 으로 묶어 정상 편차가 이상 신호로 읽히지 않게 했다.

**판정 불가 사유를 네 가지로 구분한다.** 10절의 원칙이 전세 쪽에도 적용된다.

| 상황 | 문구 |
|---|---|
| 전월세 0건 | 이 단지는 조회 기간에 전월세 거래가 없습니다 |
| 전부 월세 | 전월세 N건이 모두 월세 계약입니다 |
| 면적대 없음 | 전월세 N건이 있지만 전용 ○○㎡ 부근(±10%)에 전세 계약이 없습니다 |
| 표본 부족 | 전용 ○○㎡ 부근 전세가 N건뿐입니다 |

두 번째가 특히 중요하다. "표본 부족"으로 뭉뚱그리면 표본을 더 모으면 해결될 것처럼
읽히는데, 전부 월세인 단지는 아무리 모아도 해결되지 않는다.

### 실측 (공개 URL, 2026-09-22)

```
서울 종로구 · 경희궁자이(2단지) · 전용 84㎡ · 보증금 120,000만원 · 전세

전세 시세 대비  97.5%  시세보다 낮음   중위가 123,000만원, 전세 35건
전세가율        45.8%  안전            중위가 261,750만원, 매매 14건
출처            전월세 161건 · 매매 34건 · 해제 2건 제외
```

## 11-d. 월세 시세 대비 (2026-09-24)

### 왜 별도 지표가 필요한가

월세 계약은 숫자가 둘이고, 그 둘이 서로 맞바꾼다. 같은 단지 같은 면적에서
실제로 신고된 값들이다(경희궁자이 84㎡, 6개월, 월세 38건).

```
  4,000 / 440      50,000 / 280      90,000 / 140
 20,000 / 420      70,000 / 170     125,000 /  20
```

보증금이 오르면 월세가 내려간다. 따라서 **38건 전체의 월세 중위값(≈240)은
어떤 실제 계약도 설명하지 못한다.** 거기에 내 월세를 나누면 전월세 전환율을
암묵적으로 가정하는 것과 같다. 10절이 금지하는 바로 그 일이다.

전세 카드를 월세 계약에 그대로 쓰는 것도 안 된다. 보증금 3,000만원을 전세
중위가 123,000만원으로 나누면 2.4%에 `시세보다 낮음`이 붙는다. 종류가 다른
계약에 대해 참이 아닌 문장이다.

### 계산

```
표본 = 같은 단지 + 전용 ±10% + 월세 계약 + 보증금이 내 계약의 ±20% 이내
월세 시세 대비 = 내 월세 ÷ 그 표본의 월세 중위값 × 100

< 100%     시세보다 낮음
100~110%   시세 수준
110% ~     시세보다 높음

3건 미만 → 비교하지 않음
```

`src/lib/ratio.js`: `wolseRatio` / `wolseDistribution` / `wolseTransactions`,
밴드는 `DEPOSIT_BAND = 0.2`.

**보증금 구간을 화면에 찍는다.** 독자가 추측할 수 없는 조건이므로 반드시
보여야 한다: `보증금 16,000만원~24,000만원 구간의 5건 기준`.

실거래 표에도 보증금 칸을 넣는다. 없으면 월세들이 흩어진 값으로 보이는데,
실제로는 곡선 위의 점들이다.

### 행별 차액은 여기서만 의미가 있다

전세 카드가 월세 계약을 받았을 때는 행별 차액을 끈다. 모든 행이 전세 보증금
이라 비교 자체가 성립하지 않는다. 월세 카드에서는 모든 행이 내 보증금 ±20%
안이라 월세끼리 빼는 것이 같은 종류의 숫자를 빼는 일이 된다.

### 판정 불가 사유

| 상황 | 문구 |
|---|---|
| 전월세 0건 | 이 단지는 조회 기간에 전월세 거래가 없습니다 |
| 면적대에 월세 없음 | 전월세 N건이 있지만 전용 ○○㎡ 부근(±10%)에 월세 계약이 없습니다 |
| 보증금 구간에 없음 | 부근 월세는 N건 있지만, 보증금 ○~○ 구간의 계약이 없습니다 |
| 표본 부족 | 그 구간의 월세 계약이 N건뿐입니다 |

세 번째가 이 지표 때문에 새로 필요해진 사유다. "표본 부족"으로 뭉치면 표본을
더 모으면 해결될 것처럼 읽히는데, 실제 원인은 보증금 구간이 비어 있는 것이다.

### 실측 (2026-09-24)


## 11-e. 이 단지 최근 실거래 (2026-09-24)

매매 박스플롯 카드를 대체했다. 독자가 이름 붙일 수 없는 가격들의 차트보다
날짜가 붙은 여섯 줄이 강하고, 한 단지는 세 가지 형태로 거래되는데 분포 하나가
그것을 한꺼번에 담지 못한다.

전세·월세·매매 타일 3개. 타일 얼굴에 최신 거래 1건(날짜·면적·금액)을 싣는다.
건수만 있으면 누를 이유가 없다. 누르면 `<dialog>` 팝업이 최근 20건을 연다.

**면적 필터를 걸지 않는다.** 위 두 비교는 "이 면적에서 비싼가"를 묻고, 이
카드는 "이 단지가 요즘 얼마에 거래되나"를 묻는다. ±10%로 좁히면 대부분 단지
에서 보여줄 것이 남지 않는다. 대신 각 행에 전용면적을 찍는다.

타일에는 보여준 수가 아니라 있는 수를 쓴다(`34건`). 팝업 부제에 `최근 20건 ·
전체 94건`처럼 둘 다 적어, 20행이 전부인 것으로 읽히지 않게 한다.

해제된 매매는 목록에 넣지 않고 팝업 하단에 건수만 적는다. 해제된 거래는
무엇인가 실제로 거래된 가격이 아니며, 그것이 이 카드가 답하는 질문이다.
